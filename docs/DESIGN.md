# wechat-memory-agent 设计文档

> 个人微信文件助手 → 知识库系统。默认静默归档所有发给 bot 的内容，支持按内容检索找回。
> 本文档汇总前期讨论的所有决策，供评审与继续讨论。

- 状态：**设计讨论中（未开始编码）**
- 更新日期：2026-09-22

---

## 1. 项目定位与目标

### 1.1 核心场景
用户经常给微信"文件助手"发送文件、链接、文字、图片，希望**以后能检索找回以前发过的内容**。

典型查询（用户实际记忆方式）：
- "找回那条带发票的消息"
- "帮我查一下我之前保存的一个腾讯的开源项目链接"
- "上个月发的那个招聘岗位截图"
- "之前那个 PDF 文件"

**关键洞察**：用户检索时记得的是"大概什么时间、是文件还是链接、大概什么内容"，**不是完整关键词**。所以检索必须支持：元数据过滤（类型/时间/会话）+ 关键词 + 语义，三者结合。

### 1.2 为什么做独立 agent（而非在 hermes 上打补丁）
- 用户要完全控制架构，hermes 是参考实现而非运行环境
- 微信连接协议（iLink Bot API）从 hermes 的 `weixin.py` 移植
- 与 hermes 解耦，升级不冲突

### 1.3 核心设计原则
1. **原文永不改动**（raw 层一字不改，可追溯）
2. **按内容类型分道，不按文件后缀**（后缀初筛 + 魔数校验）
3. **所有处理本地完成**，不依赖云 API（已实测原因见 §6）
4. **默认全部入库**，`/` 开头为指令

## 2. 需求范围与边界

### 2.1 范围内
- 采集：微信 bot 收到的文字/文件/链接/图片，默认全部静默归档
- 指令：`/search`（检索）、`/list`（列表）、`/help`（帮助）等
- 检索：混合检索（关键词 + 语义 + 元数据过滤）
- 提取：PDF/Word/Excel 文本、截图 OCR、发票结构化、链接快照

### 2.2 范围外（后续增强，文档预留字段）
- 链接正文深度快照（当前先抓 title/description/摘要）
- 主动问答（基于知识库的 LLM 对话）——先不做，聚焦采集+检索
- 图片语义描述：**用户将提供支持 vision 的 LLM**，人像/纯图将可被内容检索（见 §8.3）

### 2.3 已知平台限制（重要预期管理）
- iLink bot 身份（形如 `xxx@im.bot`）**不是**普通微信号
- 通常**收不到群消息**，只有私聊 DM 可靠
- `@个人微信号` ≠ `@bot`（两个身份）
- 本场景（给文件助手发内容）正是私聊，不受影响

## 3. 微信连接层（移植自 hermes weixin.py）

### 3.1 协议：腾讯 iLink Bot API
- 传输：**长轮询**（`ilink/bot/getupdates`，35s 超时），无需 webhook/公网端口
- 登录：QR 扫码（`get_bot_qrcode` → 轮询 `get_qrcode_status` → confirmed 拿 bot_token）
- 端点：
  - `ilink/bot/getupdates` — 拉消息
  - `ilink/bot/sendmessage` — 发消息
  - `ilink/bot/getuploadurl` — 媒体上传
  - `ilink/bot/get_bot_qrcode` / `get_qrcode_status` — 登录

### 3.2 消息结构（item_list）
| type | 内容 | 关键字段 |
|---|---|---|
| 1 | 文本 | `text_item.text` |
| 2 | 图片 | `image_item.media`（CDN + AES key） |
| 3 | 语音 | `voice_item.media` / `voice_item.text`(STT) |
| 4 | 文件 | `file_item.media` + `file_name` |
| 5 | 视频 | `video_item.media` |

顶层字段：`from_user_id`、`message_id`、`item_list`、`context_token`、`room_id`、`ref_msg`(引用)

### 3.3 媒体解密
- 媒体文件经 **AES-128-ECB** 加密，通过 CDN 传输
- 下载流程：`encrypt_query_param` 构造 CDN URL → 下载密文 → `aes_key`（base64(hex)）解密 → 明文文件
- 依赖：`aiohttp`（HTTP）+ `cryptography`（AES）

### 3.4 发送（回复检索结果用）
- `sendmessage` + `context_token` 回填（会话令牌，不回填会过期）
- 错误处理：-14 会话过期（去 token 重试）、-2 限流（退避）
- 分片发送（超长文本）

### 3.5 稳定性
- `get_updates_buf` 游标持久化（断线续拉）
- 断线重连：连续失败退避（2s/30s）、session 回收
- 消息去重：5 分钟滑动窗口（message_id + 内容指纹）

### 3.6 多附件消息兼容（实测确认）
- **电脑端微信**：文字 + 附件可以在同一条消息里发送（item_list 多元素：文字 + 图 + 文件）
- **手机端微信**：文字和附件**不能同条发送**（item_list 单元素）
- **结论**：实际数据是混合的——有的消息带文字+多附件，有的纯文字/单附件
- **架构兼容性**："一条消息一个目录 + 主表/附件子表"天然兼容两种情况，无需改结构
  - 多附件消息：目录多文件，attachments 表多行
  - 纯文字消息：attachments 表 0 行
  - 弹性设计，不依赖"每条消息一定有附件"

## 4. 消息 ID 设计（关键：msg_id 从哪来）

### 4.1 问题
微信 `message_id` **不能直接当主键**：
- 不是稳定全局唯一 ID（不同会话/时间窗口可能重复）
- 可能为空（系统消息等）
- 导入外部数据时不可控

### 4.2 方案：系统生成稳定 ID
```
msg_id = "20260922-153045-<sha256片段12位>"
        └ 时间戳 └ 到达时刻   └ hash(message_id | sender | content)
```

- 时间戳保证可读性（目录名一看即知时间）
- 内容哈希保证唯一性（同一条消息重复到达 → 相同 ID → 天然去重）
- 不依赖微信 message_id 的稳定性（只是哈希输入）

### 4.3 检索流程（用户不接触 msg_id）
```
用户自然语言 → 查询解析(关键词/类型/时间/会话) → 索引搜索 → 候选列表 → 用户选择 → 内部按 msg_id 定位
```
msg_id 全程在后台，是系统内部定位钥匙，用户看到的是消息内容摘要。

## 5. 存储设计

### 5.1 物理存储：按消息单元分目录（raw 层）

```
~/wechat-memory-agent-data/
├── raw/                          # 原文文件库（永不改动）
│   └── 20260922-153045-abc123/   # 一条消息 = 一个目录（目录名=msg_id）
│       ├── message.json          # 消息元数据 + 微信原始结构
│       ├── content.txt           # 文字内容（如有）
│       ├── invoice.pdf           # 附件：发票
│       ├── screenshot.jpg        # 附件：截图
│       └── link_snapshot.json    # 附件：链接快照
├── extracted/                    # 提取层（可重建，与原文分离）
│   ├── pdf_text/                 # PDF 全文
│   ├── ocr_text/                 # 截图 OCR 文字
│   ├── zip_text/                 # 源码包文档文本
│   └── link_text/                # 链接正文快照
├── index.db                      # SQLite（元数据 + 全文索引）
└── meta/                         # 派生数据（去重哈希等）
```

**设计要点**：
- `raw/` 与 `extracted/` 严格分离：raw 是证据（一字不改），extracted 是加工品（删了可重建）
- 一条消息一个目录，目录名 = msg_id，归档/备份/迁移/删除都以目录为单位
- 文件名带 msg_id，可追溯到微信消息

### 5.2 逻辑存储：SQLite（统一骨架 + type 区分）

```
SQLite index.db
├── messages       # 主表：msg_id | 时间 | 会话 | 发送者 | 一级类型 | raw目录
├── attachments    # 附件表：msg_id(FK) | 二级类型 | 文件名 | 提取文本引用
├── documents      # LLM 元数据表：msg_id | summary | keywords | category | entities | title
├── invoices       # 发票表：msg_id | 金额 | 日期 | 商家 | 税号（结构化查询）
├── links          # 链接表：msg_id | url | title | description | fetched_at | 状态
├── extracted_text # 提取全文：msg_id(FK) | 类型 | 全文内容（大文件存文件路径）
├── fts_metadata   # FTS5：元数据(summary/keywords/category) 全文索引
└── fts_fulltext   # FTS5：提取全文 全文索引（兜底）
```

**统一 vs 差异化**：
- 逻辑上统一（messages 主表 + type 区分），因为检索要跨类型
- 物理上差异化（不同类型提取管线/产物不同）
- 检索用一级类型（document 涵盖 pdf/docx/xlsx），处理用二级子类型
- **不做 chunks 分块**：检索目标是"找文件"而非问答，用 LLM 元数据（documents 表）+ 全文兜底（fts_fulltext）

### 5.3 提取产物存放
- **大块文本**（PDF 全文、OCR 文字）→ 存 `extracted/` 文件（体积大、可重建），SQLite 存路径
- **结构化/精炼产物**（LLM 元数据、发票字段）→ 存 SQLite（被检索）

## 6. 文件类型体系（两级结构）

### 6.1 一级类型（检索过滤用）
```
text | document | image | link | binary | other
```

### 6.2 二级子类型（选提取管线用）
```
document: pdf | docx | xlsx
image:    photo | screenshot
binary:   jar | exe | archive | unknown
```

### 6.3 压缩包（zip）的处理——不单独设类型
- zip/tar.gz 是**容器**，不是文档
- 入库时浅检查（看文件名清单）：
  - 含 `.md/.txt/源码` 且大小合理 → 提取文档文本 → 归入 `document`
  - 否则（安装包/大包）→ 归入 `binary`，只存原文+元数据
- 不盲目解压大包（避免 224MB jar 耗资源）

### 6.4 各类型完整处理表

> 检索方式统一为：**LLM 生成元数据（summary/keywords/category）+ 全文 FTS5 兜底**，按类型微调。

| 一级 | 二级 | 原文 | 提取管线 | 提取产物 | 检索方式 |
|---|---|---|---|---|---|
| text | — | raw/*.txt | 无 | 内容直接可索引 | LLM 元数据 + 全文 |
| document | pdf | raw/*.pdf | PyMuPDF | 全文 + LLM 元数据 | 元数据 + 全文兜底 |
| document | docx | raw/*.docx | python-docx | 段落全文 + LLM 元数据 | 元数据 + 全文兜底 |
| document | xlsx | raw/*.xlsx | openpyxl 逐sheet | sheet全文 + LLM 元数据 | 元数据 + 全文兜底 |
| invoice | — | raw/*.pdf | PyMuPDF+字段提取 | invoices表 + LLM 元数据 | 字段 + 元数据 + 全文 |
| image | screenshot | raw/*.jpg | RapidOCR | OCR文本 + LLM 元数据 | 元数据 + OCR全文 |
| image | photo | raw/*.jpg | vision 描述 | LLM 描述 + 元数据 | 元数据 |
| link | — | raw/link_snapshot.json | 网页快照 + LLM 元数据 | links表 + 元数据 | URL + 元数据 + 全文 |
| binary | jar/exe/... | raw/*.jar | 不解析 | 无 | 仅浅层元数据 |
| other | 未知 | raw/* | 仅元数据 | 无 | 仅元数据 |

### 6.5 文件分类：后缀初筛 + 魔数校验
- **后缀**：快速初筛（.pdf/.docx/.xlsx/.jpg/.zip...）
- **魔数**（文件头固定签名字节）：校准真实类型，防改后缀
  - `%PDF` → PDF
  - `PK` → zip 容器（再细分：docx/xlsx/jar/zip）
  - `\xFF\xD8\xFF` → JPEG，`\x89PNG` → PNG
  - `MZ` → exe/dll
- 魔数认不出 → `other`，只存元数据
- 微信 temp 文件常为无意义哈希名，靠魔数而非后缀判断

### 6.6 大二进制文件策略
- >10MB 或已知编译产物（jar/exe）→ **只做浅层元数据**（文件名/大小/哈希/日期），不解析
- 原文仍存 raw/（可追溯），但不提取、不生成元数据（无检索价值）

## 7. 链接类型（与普通文本的本质区别）

### 7.1 为什么不能当普通文本
用户要检索的是"链接指向什么"（内容），不是链接字符串本身。
例：用户存 `https://github.com/Sherlockwz/T-Mem`，后来搜"腾讯的开源项目"——**URL 里没有"腾讯"二字**，只存 URL 永远搜不到。必须抓快照。

### 7.2 快照抓取（已实测验证）
抓取结果（T-Mem 实测）：HTTP 200，title + description + README 正文 10646 字符全部可提取。

```
链接进来 → 抓取 → 存：
  url | title | description | body_excerpt | full_text_ref | fetched_at | fetch_status
```

### 7.3 存储
- 物理：`raw/<msg_id>/link_snapshot.json`
- 逻辑：SQLite `links` 表（独立，因有 url/fetch_status 特有字段）+ LLM 元数据（documents 表）
- 检索：FTS5（title/desc/body + LLM 元数据）、URL 片段、元数据过滤

### 7.4 抓取策略
| 情况 | 处理 |
|---|---|
| 普通网页/GitHub | 抓 title + description + 正文摘要 |
| 抓取失败/超时 | 只存 URL + `fetch_status=error`，可重试 |
| 无正文（视频页等） | 至少 title |

**快照价值**：入库时抓一次存住，以后链接失效/内容变更，仍可检索"当时保存的内容"。

## 8. 图片处理

### 8.1 流程（预判 + 按需处理）
```
图片进来
  ├─ 轻量预判（尺寸比例/白底占比/边缘密度）
  ├─ 判定为截图/含文字 → RapidOCR 提取文字
  ├─ 判定为人像/纯图 → 原图存档 + 语义描述（见 8.3）
  └─ 无论哪种：原图永久存档 raw/
```

### 8.2 实测验证
- RapidOCR：2.8s 识别 31 行文本（BOSS直聘招聘截图，"AI应用全栈工程师"等）
- 截图识别准确，证明本地 OCR 方案可行

### 8.3 图片描述机制（多来源合并）

**背景**：微信私聊图片不能带伴随文字（item_list 无文字），但电脑端文字+附件可同条发送。图片的检索文本需要多来源合并，最终与"LLM 生成元数据"方案统一。

**描述来源（按可靠度）**：
1. **同消息伴随文字**（电脑端）：同一条消息里的文字 → 最可靠，直接写入 description
2. **用户显式指代**：相邻文字明确指代"这张图/上图" → 才建立关联
3. **Vision LLM 生成**（用户提供 vision API）：无以上来源时，生成一句话描述 + 元数据
4. **元数据**（时间/会话）：始终作为辅助检索字段

**描述管线**：
```
图片（属于某消息）
  ├─ 同消息有文字 → description = 伴随文字（vision 可选补充）
  ├─ 无伴随文字 → vision LLM 生成描述（一句话 + category + keywords）
  └─ description + 元数据 → documents 表 + FTS5 → 可检索
```

**与 LLM 元数据方案统一**：图片的 vision 描述 = 图片的 LLM 元数据（summary），与 document 的 LLM 元数据机制一致，统一存 documents 表。

### 8.4 相邻消息处理原则：入库不猜，检索聚簇

**问题**：微信里"先发文字、后发图"是两条消息，无法可靠判断"相邻文字是否在描述这张图"（中间可能插话/换话题）。

**原则**：
- **入库时不自动绑定**相邻消息（避免错误关联污染数据）
- 只有可靠信号才写入 description：同消息文字、显式指代
- **检索时软聚簇**：同一会话 + 短时间相邻的消息，展示时一起列出，让用户自己判断
- 区分两个概念：
  - **硬绑定**（强关联）：同消息附件、显式指代 → 写入字段
  - **软聚簇**（弱关联）：会话+时间相邻 → 检索时聚合展示，不写入字段

**关键权衡**：入库的错误关联是数据污染（难清理），比检索不准更糟。宁可检索多召回让用户挑，也不要把错误关联写死。

## 9. 技术选型与已验证的环境

### 9.1 LLM API 探测结果（决定架构方向）

| API | 状态 | 结论 |
|---|---|---|
| 腾讯 LKEAP（api.lkeap.cloud.tencent.com） | `/models` 有；`/embeddings` **404**；对话**配额耗尽 429** | 不可用，且不支持 embedding |
| opencode zen（opencode.ai/zen/v1） | 全部 **403**（Cloudflare 拦截） | 不可用 |

**结论**：图片 OCR 处理**走本地**，不依赖云 API。LLM 元数据生成（含 vision 图片描述）由**用户提供可用的 LLM API**（已确认可用，接口细节待补充）。

### 9.2 本地技术栈（已全部验证可用）

| 能力 | 库 | 验证结果 |
|---|---|---|
| 本地 OCR | rapidocr_onnxruntime | ✅ 2.8s 识别 31 行 |
| PDF 提取 | PyMuPDF (fitz) / pypdf | ✅ 已装 |
| Word 提取 | python-docx | ✅ 已装 |
| Excel 提取 | openpyxl / xlrd / pandas | ✅ 已装 |
| 网页抓取 | requests + bs4 + lxml | ✅ T-Mem 抓取成功 |
| 数据库 | SQLite (内置 FTS5) | ✅ 系统自带 |

> 注：**不使用 embedding/向量库**。语义扩展由 LLM 生成 keywords 覆盖（见 §9.3），因此不依赖 sentence_transformers/BGE，也不依赖专用向量库。

### 9.3 检索方案：LLM 生成元数据 + 全文兜底（无 embedding）

**核心决策**：用户需求是"把文件找出来"，不是"知识问答"。因此**不做 chunks 分块、不做向量 embedding**，改为 **LLM 生成文件元数据 + 全文 FTS5 兜底**。

**LLM 生成元数据**（每个文件/图片/链接入库时处理一次）：
```
LLM 读取提取的全文 → 生成结构化元数据：
  {
    "summary":    "这是一份关于XX的文档，主要讲...",
    "keywords":   ["RAG", "检索增强", "知识库"],
    "category":   "技术文档",        // 发票/报告/合同/截图/人像...
    "entities":   ["Alice", "公司A", "2026年"],
    "title":      "XX报告"
  }
```

**检索双通道**：
1. **元数据 FTS5（主力）**：summary + keywords + category 建 FTS5 全文索引 → 命中即得，可结构化过滤（搜"发票"直接过滤 category）
2. **全文 FTS5（兜底）**：提取的全文建 FTS5 → 搜到元数据漏掉的细节词

**为什么不需要 embedding（向量）**：
- 向量语义搜索的核心价值是"同义改写匹配"（搜"检索增强工具"能命中写"RAG"的文档）
- 这个价值被 **LLM 生成的 keywords 吸收**了：LLM 提炼 keywords 时已把同义词/核心概念扩展进去（["RAG","检索增强","知识库"]），FTS5 直接命中
- 所以向量变成冗余层，还带来额外成本（模型加载、存储、维护）
- 若未来需要知识问答（精读找答案），再引入向量不迟；当前"找文件"场景不需要

**成本**：每文件一次 LLM 调用（读全文生成元数据），每周 <50 份完全可接受。

**推广到其他类型**：
- 图片：LLM 生成描述（= vision 描述，统一机制）
- 链接：快照正文 → LLM 生成 summary/keywords
- 发票：LLM 提取结构化字段（金额/日期/商家）→ invoices 表

**依赖**：本方案依赖**可用的 LLM API**（对话生成元数据）。用户已确认有可用 LLM，不需担心。除此之外不依赖任何 embedding 模型或向量库。

## 10. 指令系统设计

- 默认消息 → 全部静默入库
- `/` 开头 → 指令，不入库

### 10.1 指令形式：`/` + 自然语言
用户直接输入自然语言查询，无需记结构化语法：
```
/帮我查一下最近一个月我上传的一个压缩包
/查一下那个腾讯的开源项目
/上周的发票
/RAG
```

**分流规则**：
- `/` + 固定词（`help`、`list` 等）→ 固定指令
- `/` + 其他 → 当作自然语言查询（即使没有"帮我查"前缀，如 `/RAG`）

### 10.2 查询解析：规则优先 + LLM 兜底（带历史与库内快照）

**第一层：规则解析（优先，本地、免费、可靠）**
从自然语言提取结构化条件：
| 提取项 | 示例 | 映射 |
|---|---|---|
| 时间词 | 最近一个月/上周/上个月/昨天 | 时间范围（30d/上周/上月/1d） |
| 类型词 | 压缩包/发票/截图/文档/链接 | 类型过滤（binary/invoice/image/document/link） |
| 关键词 | 其余内容 | FTS5/LIKE 搜元数据+全文 |

**第二层：LLM 兜底（按需触发，非每次调用）**

触发条件（满足其一才调 LLM）：
1. 查询含**指代词**（那个/刚才/上次/它/再搜/还是）→ 需要对话历史才能理解
2. 规则解析**全空**（类型/时间/关键词都没提取到）
3. 搜索 **0 命中** → LLM 兜底改写/直选

**LLM 兜底读取的两块上下文（都是按需临拼，非常驻）：**

| 上下文 | 内容 | 回答的问题 | 大小 |
|---|---|---|---|
| **最近 1 轮对话** | 上一轮查询原文 + 解析摘要 + top3 结果标题 | "用户刚才在聊什么？"（指代消解） | ≤300 字 |
| **知识库快照** | 库内最近 20 条的 title+keywords+category 清单 | "库里实际存了什么词？"（改写有靶子） | ≤2000 字 |

- 快照**不是常驻上下文**：临查临拼、用完即弃，每次 LLM 调用独立无状态
- 常规查询（规则解析完整且有命中）**零 LLM 调用、零 token**
- 快照只含元数据（标题/关键词/分类），不含全文和原文路径
- 喂 LLM 前过 desensitize 脱敏（与 §11.2 一致）

**0 命中兜底的双输出设计**（LLM 一次输出两种可能）：
```
0 命中 → LLM（快照 + 最近1轮 + 当前查询）输出：
  {
    "match_id": "...",                          ← 快照里直接能选中（优先）
    "rewritten": {"keywords":"招聘", "type":"image"}  ← 选不中时的改写兜底
  }
执行：
  ├─ match_id 有效 → 直接返回该条（标注"近似匹配"），零重搜
  ├─ 否则用 rewritten 重搜 1 次（可命中快照之外的更早记录）
  └─ 都没有 → "没找到"
```
直接挑优先于改写：快照能选中说明答案就在眼前，不必再绕索引；改写兜底覆盖答案在 20 条之外老记录的情况。

**防护参数：**
| 参数 | 值 |
|---|---|
| 每查询 LLM 上限 | 2 次（解析 1 + 兜底 1） |
| LLM 超时 | 8s，失败退回规则结果 |
| 历史轮数 | 1（只读最近 1 轮；对话原子化，跨轮指代罕见） |
| 历史读取时机 | 仅指代词触发 / 规则解析全空 / 0 命中 |
| 历史存储 | 内存，重启即失（不做持久化） |
| 反问澄清 | v1 不做（模糊查询按最佳猜测直接搜） |

### 10.3 类型词映射表（默认版，可用户自定义）
| 用户说法 | 类型 |
|---|---|
| 压缩包/zip/rar | binary |
| 发票 | invoice |
| 截图/图片/照片 | image |
| 文档/PDF/Word/Excel | document |
| 链接/网址/url | link |
| 源码/代码/项目 | document（zip_source） |

> 注意：不放单字词（如"图"），避免误判（"图记忆/图书馆/地图"都会被带偏）。

### 10.4 检索执行
```
解析出 (类型/时间/关键词)
  ├─ WHERE type=... AND 时间范围...
  ├─ FTS5 搜关键词（元数据优先，全文兜底）
  └─ 合并排序 → 摘要列表返回
```

### 10.5 检索结果展示与交互

**展示：按相关性排序的可扫读卡片列表**
```
🔍 找到 3 条相关记录：

① 📄 文档 | 2026-08-22 | RAG实践指南.pdf
   匹配: 关键词"RAG" 命中元数据
   > 关于检索增强生成(RAG)的实践... (摘要前60字)

② 🖼️ 截图 | 2026-09-14 | BOSS直聘岗位截图
   匹配: 关键词"RAG" 命中OCR文字
   > AI应用全栈工程师，负责企业系统集成...

③ 🔗 链接 | 2026-07-30 | T-Mem 记忆系统
   匹配: 语义近似(LLM元数据)
   > Memory That Anticipates, Not Archives...
```

**卡片字段**：序号 + 类型图标 + 日期 + 标题 + 匹配原因 + 摘要（summary 前 60 字）
**类型图标**：📄文档 / 🖼️截图图片 / 🔗链接 / 🧾发票 / 📦压缩包 / 💬文字
**显示上限**：默认最多 5-8 条，避免刷屏；更多可用 `/more` 翻页或收窄条件

**交互：`/序号` 选择条目**（不是裸数字 `1`）
```
用户: /帮我查一下最近一个月的压缩包
系统: 🔍 找到 3 条相关记录：①②③...
用户: /1              ← /序号 选择，与 / 指令系统统一
系统: 📦 xxx.zip 详情...
     [已发送原文件 xxx.zip]   ← 回传原文件/原图，完成"找到→拿到"闭环
```

**为什么用 `/1` 而非 `1`**：
- 与 `/` 指令系统统一（都进指令解析，不入库）
- 无歧义：`/1` 明确是"选择条目"，裸 `1` 需猜测是选择还是聊天
- 避免误入库：裸 `1` 会被当成普通消息归档
- 可扩展：`/1`、`/more`、`/1 detail` 语法一致

## 11. 数据治理边界

**核心前提**：发送消息的人是自己（单用户场景），因此数据治理策略大幅简化。

### 11.1 已确认决策
- **无垃圾信息问题**：发送者是自己 → 不存在广告/营销软文/验证码等垃圾内容，无需垃圾过滤
- **无需内容级去重**：自己发的消息，重复内容不必特殊处理（消息级去重由 msg_id 机制已覆盖，见 §4）
- **敏感信息脱敏**：发送给 LLM 生成元数据时，先做脱敏处理（身份证/银行卡/手机号等敏感信息，在送 LLM 前用规则脱敏，如打码/替换），原文本地存储不动

### 11.2 脱敏策略（参照 hermes redact.py 完善）

- **时机**：仅在调用 LLM 前脱敏（元数据生成、图片描述、LLM 兜底解析/改写的 prompt）
- **原则**：原文 raw/ 永远保留原始内容，脱敏只发生在"内容送往 LLM"这一步

**两类模式（合并 hermes 凭证模式 + 中文 PII 扩展）：**

| 类别 | 模式 | 掩码方式 |
|---|---|---|
| 凭证前缀 | sk-/ark-/ghp_/xox/AIza/AKIA/glpat- 等 27+ 厂商 | 短token全掩，长token保头6尾4 |
| KEY=VALUE | API_KEY=/password:/token: 等赋值 | 值掩码，保留键名 |
| URL 敏感参数 | ?token=/&code=/&signature= 等 | 值替换 *** |
| JWT / 私钥 | eyJ.../-----BEGIN PRIVATE KEY----- | 整块 [REDACTED] |
| 身份证 | 18位（含X） | 保头3尾3 |
| 手机号 | 1[3-9]xxxxxxxxx | 保头3尾3 |
| 银行卡 | 16-19位数字 | 保头3尾3 |
| 座机 | 0xx-xxxxxxxx | 保头3尾3 |
| 邮箱 | 标准格式 | 用户名保头2，域保留 |

**性能预检**（hermes 模式）：每类正则先做廉价子串预检（含凭证关键词/数字串/@符号），无命中线索直接跳过，常规文本零正则开销。
